## Contexto

La 0.3 de `docs/PLAN.md` asume `supabase start`, que levanta el stack en contenedores. Esta máquina es
Windows sin WSL2 y sin Docker (verificado: ni `docker` ni `supabase` en PATH, no existe
`C:\Program Files\Docker`). El stack local no es una opción.

**El cambio**: la base de desarrollo pasa a ser el proyecto Supabase hosteado `recepcionista-ia-dev`.
El esquema se aplica con `supabase db push` contra el proyecto vinculado y los tipos se generan desde
ese mismo proyecto. Se aprovecha para migrar a las API keys nuevas (`sb_publishable_` / `sb_secret_`).

**El objetivo y la Verificación de 0.3 no cambian**: esquema aplicado, `src/lib/db/types.ts` generado,
Dental Nova cargada con 6 servicios, y `book_appointment` lanzando `SLOT_TAKEN` con dos turnos solapados.

### Por qué funciona sin Docker (verificado)

| Cosa | Veredicto |
|------|-----------|
| `supabase gen types --linked` | Llama al endpoint `GET /v1/projects/{ref}/types/typescript` de la Management API con el Bearer token. **No usa Docker.** `--local` y `--db-url` sí levantan un contenedor `pg-meta` → no sirven como fallback. |
| `supabase db push` | El handler nativo conecta a Postgres directo. No usa Docker. |
| `DATABASE_URL` para pg-boss | **Session pooler, puerto 5432.** IPv4 en todos los tiers, 1:1 cliente↔backend → soporta LISTEN/NOTIFY, advisory locks y prepared statements. |

**Los tres modos de conexión**:

- Directa (`db.<ref>.supabase.co:5432`) — IPv6-only salvo add-on pago. Falla con `ENETUNREACH` si la red no rutea IPv6.
- **Session pooler (`aws-<n>-<region>.pooler.supabase.com:5432`) ✅** — la elegida.
- Transaction pooler (`:6543`) ❌ — sin prepared statements, sin LISTEN/NOTIFY, sin advisory locks. Rompe pg-boss.

**Tres detalles que rompen si se ignoran**:

1. El usuario del pooler es `postgres.<PROJECT_REF>`, no `postgres`. Es el error "Tenant or user not found".
2. El prefijo de región del host (`aws-0-` vs `aws-1-`) varía por proyecto → copiar la cadena del Dashboard, no escribirla a mano.
3. ~~`?sslmode=require` sin `sslrootcert` produce `ssl: { rejectUnauthorized: false }`.~~ **Falso, verificado en la Fase D**: en `pg@8.23` `sslmode=require` es alias de `verify-full` y tira `SELF_SIGNED_CERT_IN_CHAIN` contra Supabase. La config va en el objeto `ssl` del cliente y el param se saca de la URL — con manipulación de string, porque `new URL().toString()` percent-encodea el password y `pg` no lo decodifica de vuelta (28P01). Vale para `scripts/seed.ts` y para pg-boss en 1.3.

**API keys nuevas**: `sb_publishable_` reemplaza a `anon`, `sb_secret_` reemplaza a `service_role`.
`createClient(url, key)` no cambia de forma. RLS sigue aplicando a la publishable; la secret sigue
haciendo bypass. Único caveat (no nos afecta): no son JWTs, van en el header `apikey`, no en
`Authorization: Bearer`. supabase-js ya las manda ahí.

const path = "src/lib/db/types.ts";
const b = readFileSync(path);

if (b.length < 500) throw new Error(`${path}: empty or truncated (${b.length} bytes)`);

## Riesgos y qué hacer

- **`db push` con IPv6.** Resuelve la conexión por su cuenta y puede intentar el host directo
  `db.<ref>.supabase.co`. Si falla con `ENETUNREACH`/`EHOSTUNREACH`, reintentar con
  `pnpm supabase db push --db-url "$DATABASE_URL"`. En `db push`, `--db-url` es solo una cadena de
  conexión — a diferencia de `gen types`, acá no levanta ningún contenedor.
- **`0001_init.sql` toca `auth.users` (`conversations.assigned_to`) y `supabase_realtime`.** En el
  proyecto hosteado esos objetos existen, así que debería pasar. Si falla por permisos: **parar y
  mostrar el error crudo.** No editar la migración ni crear una `0002` por cuenta propia.
- **Escape hatch si el push sale mal**: existe `supabase db reset --linked`, que resetea la base
  remota desde `supabase/migrations/`. Es destructivo, pero en un proyecto `-dev` es aceptable.
  Igual: `--dry-run` primero, siempre.
- **`supabase init` con la carpeta ya existente**: si tira "already initialized" es porque
  `config.toml` ya está. No usar `--force` sin mirar qué sobrescribe.
